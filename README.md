# DevBox

Рабочая среда в контейнере: открыл окно VS Code — внутри уже лежат твои репозитории, инструменты,
секреты и расширения.

Это образ, который при старте запускает готовые инструменты — mise, mani, fnox — по их же родным
конфигам. Что должно быть в среде, описывают четыре файла в скоупе; на хосте остаются только образ и
тома. Своего у девбокса — команда `devbox` (стартовые конфиги нового скоупа, запуск агента, ручной
линк приложения на локальный пакет соседа) и расширение редактора с кнопками поверх неё.

## Как подключить

На хосте нужна одна папка с одним файлом — `.devcontainer/devcontainer.json`:

```json
{
  "image": "ghcr.io/egor6-66/devbox:<версия>",
  "workspaceMount": "source=devbox-repos,target=/workspaces/tree,type=volume",
  "workspaceFolder": "/workspaces/tree",
  "mounts": [
    "source=devbox-secrets,target=/home/node/.secrets,type=volume",
    "source=devbox-tools,target=/home/node/.tools,type=volume",
    "source=devbox-store,target=/home/node/.pnpm-store,type=volume"
  ],
  "customizations": {
    "vscode": {
      "extensions": ["eamodio.gitlens", "spmeesseman.vscode-taskexplorer"]
    }
  }
}
```

Дальше — `Dev Containers: Reopen in Container`. Имена томов свои: один набор томов — один скоуп.

Это единственный файл на хосте: положил и забыл. Расширения из списка редактор ставит сам при
создании контейнера. Добавить расширение насовсем можно не открывая файл: в панели расширений, в
меню расширения — **Add to devcontainer.json**. Поставленное кликом, но не внесённое в список,
живёт до следующего Rebuild.

| Том | Куда | Что в нём |
|---|---|---|
| репозитории | `/workspaces/tree` | скоуп: конфиги и репозитории |
| секреты | `/home/node/.secrets` | ключ age, логины |
| инструменты | `/home/node/.tools` | то, что поставил mise |
| кэш пакетов | `/home/node/.pnpm-store` | кэш загрузок pnpm |

Тома образ не объявляет намеренно: их называет человек, и это его состояние.

## Новый скоуп

На новых томах скоуп пуст: окно открывается без ошибок, но и без конфигов. Стартовый набор
раскладывает панель **DevBox** (значок слева) — кнопка **«Создать конфиги скоупа»**. То же из
терминала:

```sh
devbox init
```

Появляются папка `.devbox` с конфигами (инструменты, репозитории, MCP для агентов, линки, свои
скрипты), файл окна `tree.code-workspace` и две ссылки, которые нужны инструментам по их правилам
поиска. Существующее не трогается: конфиг, который вы уже правили, шаблон не перезапишет.

Дальше — вписать свои репозитории в `.devbox/mani.yaml`, добавить их папки в `tree.code-workspace`
и пересоздать контейнер (`Dev Containers: Rebuild Container`): инструменты поставятся, репозитории
склонируются.

## Четыре конфига скоупа

Лежат в `/workspaces/tree/.devbox` и видны в эксплорере. Каждый — родной формат своего инструмента.

### `mise.toml` — инструменты

```toml
[tools]
gh = "latest"
fnox = "latest"
age = "latest"
mani = "latest"
pnpm = "11.17.0"
```

Имена инструментов — из реестра: `mise registry`. Версию pnpm стоит назвать ту же, что закрепили
репозитории скоупа.

### `mani.yaml` — репозитории и их адреса

```yaml
projects:
  web-core:
    url: https://github.com/example/web-core.git
    path: ../web-core
    tags: [base]
    remotes:
      work: https://git.example.com/team/web-core
```

Пути считаются от папки конфига, поэтому каждый репозиторий — `../имя`. Адреса (`remotes`)
приводятся к конфигу при каждом подключении редактора: названное в нём ставится, поставленное
руками мимо него — убирается.

### `fnox/config.toml` — секреты

```toml
default_provider = "age"

[providers.age]
type = "age"
recipients = ["age1…"]
```

Значения лежат шифртекстом — файл можно переносить; читает их тот, у кого ключ. Задать секрет —
`fnox set -g ИМЯ` (без `-g` fnox заведёт отдельный файл в текущей папке). Подать в команду —
`fnox exec -- команда`.

### `tree.code-workspace` — окно редактора

```json
{
  "folders": [
    { "name": "web-core", "path": "web-core" },
    { "name": ".devbox", "path": ".devbox" }
  ],
  "settings": {}
}
```

Сам файл лежит в корне скоупа; в `.devbox` на него стоит ссылка, чтобы он был виден рядом с
остальными. Папки окна и общие настройки редактора — здесь; список расширений — в
`devcontainer.json`.

## Линк на локальный пакет

По умолчанию приложение берёт пакеты из реестра, как везде. Когда нужно править пакет соседнего
репозитория и сразу видеть правку в приложении, его линкуют на локальную папку — руками, на время.
При старте контейнера девбокс ничего не линкует.

Что куда линковать, описывает `.devbox/links.yaml`:

```yaml
statboard:              # куда — приложение
  web-core:             # откуда — соседний репозиторий
    - ui                # что — пакеты: имя, его хвост после `/` или имя папки
    - router

neurobox:
  web-core: all         # все пакеты соседа, которые приложение использует
```

```sh
devbox link statboard      # прилинковать, как написано в конфиге
devbox unlink statboard    # вернуть как было
```

Без имени команды идут по всем приложениям из конфига.

`link` дописывает в `pnpm-workspace.yaml` приложения блок `overrides` со ссылками на папки пакетов
и запускает его `pnpm install` — то же, что `pnpm link <папка>`, только сразу для всех названных
пакетов. pnpm при этом переписывает lock-файл приложения. **Эти два файла не коммитят, пока линк
стоит**; `unlink` откатывает их через git и ставит пакеты из реестра заново. В репозиторий соседа
не пишется ничего, и ни один репозиторий о девбоксе не знает.

Если в этих двух файлах уже есть ваши незакоммиченные правки, `link` откажется: откат затёр бы их.

## Свои скрипты и сценарии

Именованные команды скоупа пишутся в родной файл задач VS Code — `.devbox/.vscode/tasks.json`.
Task Explorer показывает их под папкой `.devbox` и запускает кликом.

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "линк: statboard → web-core",
      "type": "shell",
      "command": "devbox link statboard"
    }
  ]
}
```

Файл обязан лежать в подпапке `.vscode` — так требует редактор. Когда он появляется в папке
впервые, Task Explorer замечает его после `Developer: Reload Window`.

## Запуск агента

Роли агентов лежат в самих репозиториях — `.claude/roles/<роль>.json`. Запустить агента в нужном
репозитории с нужной ролью:

```sh
devbox agent                    # список всех ролей скоупа, выбор по номеру
devbox agent statboard main     # сразу
```

Это `claude --settings .claude/roles/main.json -n "statboard · main"` в папке репозитория. Имя
сессии Claude Code сам пишет в заголовок терминала, поэтому вкладка называется «statboard · main» —
видно, кто где. Чтобы вкладка показывала заголовок от программы, в `tree.code-workspace` стоит
настройка:

```json
"settings": { "terminal.integrated.tabs.title": "${sequence}" }
```

То же самое кликом — панель **«Агенты»** расширения DevBox (значок слева): дерево «репозиторий →
роли», собранное с диска. Клик открывает терминал с именем и цветом репозитория и зовёт
`devbox agent`; запущенный агент отмечен, повторный клик показывает уже открытый терминал.
Расширение едет в образе и ставится само, публиковать его никуда не нужно.

Из Task Explorer агента запускать не стоит: терминалу задачи (`tasks.json`) редактор даёт имя
задачи и заголовок от программы на вкладку не пускает.

## MCP-серверы для агентов

Что доступно Claude Code во всех репозиториях скоупа, описывает `.devbox/mcp.json` — в его же
родном формате. В корне скоупа на файл стоит ссылка `.mcp.json`: по этому имени Claude Code и ищет
конфиг, поднимаясь вверх от репозитория.

```json
{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": [
        "-y", "chrome-devtools-mcp@latest",
        "--executablePath", "/usr/bin/chromium",
        "--headless", "--chromeArg=--no-sandbox", "--isolated"
      ]
    }
  }
}
```

Свой сервер дописывается ещё одним блоком в тот же файл. Если у репозитория есть собственный
`.mcp.json`, серверы складываются; при совпадении имён побеждает репозиторий. В сами репозитории
девбокс ничего не кладёт.

При первом запуске `claude` в репозитории он один раз спросит, доверять ли серверам из этого файла.

## Браузер — по выбору

Браузера в образе нет. Кому он нужен, добавляет в `features` своего `devcontainer.json` готовую
фичу «поставь системные пакеты»:

```json
"ghcr.io/devcontainers-extra/features/apt-packages:1": {
  "packages": "chromium,fonts-liberation"
}
```

Один браузер служит обоим:

- **человеку** — команда `chromium` в терминале окна: редактор пробрасывает экран в контейнер, и
  окно появляется на рабочем столе;
- **агенту** — через `chrome-devtools` из `mcp.json` выше. Флаг `--headless` прячет его окно;
  уберите — и будет видно, что агент делает на странице.

Chromium из Debian, а не Google Chrome: Chrome под Linux собирают только для amd64. Шрифт нужен,
чтобы на снимках экрана был текст.

В контейнере Chromium не может завести собственную песочницу и без флага `--no-sandbox` не
стартует. Образ кладёт этот флаг в его папку настроек (`/etc/chromium.d`), поэтому команда
`chromium` работает как есть.

Нет браузера, а `chrome-devtools` в `mcp.json` указан — этот сервер у агента не запустится,
остальные работают.

## Что происходит при старте

Всё — при подключении редактора к контейнеру:

1. сам редактор ставит расширения из `devcontainer.json` и расширение девбокса из образа;
2. `mise install` — инструменты из `mise.toml`. Когда всё уже стоит, это миг;
3. `mani sync` — клонирование репозиториев и приведение их адресов, если есть `mani.yaml`.

При подключении, а не при создании контейнера: закрытым репозиториям нужен логин, а его в
контейнер передаёт редактор; и конфиги могут появиться уже после создания — как на новом скоупе.

Расширения встают раньше, чем клонируются репозитории, и порядок этот задаёт редактор. Поэтому при
самом первом запуске на пустом томе Task Explorer осматривает ещё пустые папки: один раз нажмите в
нём «обновить» или сделайте `Developer: Reload Window`. Дальше репозитории уже лежат, и этого нет.

Больше при старте не происходит ничего. Библиотеки репозиториев ставит человек командами самого
репозитория; свои скрипты — в `.devbox/.vscode/tasks.json`, по клику.

## Первая настройка на новой машине

Секреты не заработают, пока нет ключа: это личный секрет человека на конкретной машине, из конфига
он появиться не может.

```sh
age-keygen -o ~/.secrets/age.txt     # создать ключ
age-keygen -y ~/.secrets/age.txt     # показать его открытую половину
```

Открытую половину вписать в `recipients` в `fnox/config.toml`. Если секреты там уже есть, после
правки списка — `fnox reencrypt` на машине, где они читаются.

Перенос готового скоупа на другую машину одним файлом девбокс пока не умеет: на новой машине
скоуп начинают со стартовых конфигов (`devbox init`) и вписывают своё.

## Если что-то не поднялось

- **Инструментов нет:** `mise install`, затем `mise ls`.
- **Репозиторий не склонировался:** `mani sync --status`, повторить — `mani sync --sync-remotes`.
- **Расширение не встало:** проверить его имя в `customizations.vscode.extensions`.

## Разработка девбокса

### Устройство

Собственный код — TypeScript, одно ядро и два тонких входа в него:

```
src/
  core/        логика: скоуп и его пути, агенты, линки, стартовые конфиги
  cli/         команда devbox — разбор аргументов и вызов core
  extension/   расширение редактора — кнопки и панели, зовёт тот же core
templates/     стартовые конфиги скоупа, обычными файлами
extension/     описание расширения для редактора и его значок
test/          тесты ядра и проверки образа
Dockerfile
```

Правила, которые это задаёт:

- логика живёт в `core`; команда и расширение её не дублируют, а зовут;
- у каждой фичи свой файл в `core` и свои тесты; новая фича — новый файл;
- чужие программы (git, pnpm) ядро зовёт через одно место, `core/process.ts`, — через него же
  тесты подменяют то, что в проверке запускать незачем;
- в образ едет только собранное: команда одним файлом и расширение. Исходников, зависимостей и
  сборщика в образе нет.

```sh
pnpm install
pnpm typecheck     # типы
pnpm test          # тесты ядра
pnpm build         # dist/devbox.mjs и dist/devbox.vsix
```

### Проверка в окне

Фича проверяется в живом окне редактора, без публикации образа.

**Два образа, два имени.** `devbox:dev` собирается из этого репозитория локально и никуда не
уходит. `ghcr.io/egor6-66/devbox:<версия>` — опубликованный, на нём стоят рабочие скоупы.

**Тестовое окно** — отдельная папка на хосте со своим `devcontainer.json`, как в разделе «Как
подключить», только образ в нём — `devbox:dev`, а тома свои, тестовые. На опубликованный образ это
окно не переводится никогда: иначе для проверки пришлось бы публиковать.

**Цикл:**

```sh
docker build -t devbox:dev .     # собрать локальный образ (сам собирает и код)
sh test/image.sh                 # проверить его — те же проверки гоняет GitHub
```

Дальше в тестовом окне — `Dev Containers: Rebuild Container`, и смотреть, что поднялось. Правка
образа без Rebuild до окна не доезжает: команды старта редактор читает из метки образа при создании
контейнера.

Там, где docker проброшен с хоста и зовётся иначе, команду называют целиком:

```sh
DOCKER="sudo -n docker -H unix:///var/run/docker-host.sock" sh test/image.sh
```

**Проверка с нуля.** Уверенность даёт только старт на пустых томах: оставить в тестовом скоупе
конфиги (`.devbox` и `tree.code-workspace`), убрать репозитории, вычистить тома инструментов и
кэша — и Rebuild. Всё, что среда обещает, должно встать само. Ключ age при этом можно не трогать:
образ его не создаёт.

**Правка конфигов скоупа** Rebuild не требует, если применить её руками: `mise install`,
`mani sync --sync-remotes`. Сами по себе команды старта повторяются только при Rebuild —
`Developer: Reload Window` их не вызывает.

## Выпуск

Тег вида `v1.2.3` на `main` собирает образ под две платформы и публикует его в
`ghcr.io/egor6-66/devbox`. Предвыпуск (`v1.0.0-rc.1`) выходит только полной версией и не сдвигает
`latest`. Опубликованный образ проверяется один раз отдельным скоупом — не тестовым окном.
